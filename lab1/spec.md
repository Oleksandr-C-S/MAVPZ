# Spec: Завдання 1 — ER-модель бронювання аудиторій

## Намір

Змоделювати дані, необхідні для системи бронювання навчальних аудиторій університету.

Модель повинна показати основні сутності, їх атрибути, первинні та зовнішні ключі,
а також зв'язки і кардинальності між сутностями.

## Сутності

### User

Зберігає інформацію про користувачів системи.

Атрибути:
- `user_id` — унікальний ідентифікатор користувача, PK
- `full_name` — ім'я користувача
- `email` — електронна пошта користувача, унікальне значення

### Building

Зберігає інформацію про університетські корпуси.

Атрибути:
- `building_id` — унікальний ідентифікатор корпусу, PK
- `name` — назва корпусу
- `address` — адреса корпусу

### Room

Зберігає інформацію про навчальні аудиторії.

Атрибути:
- `room_id` — унікальний ідентифікатор аудиторії, PK
- `building_id` — ідентифікатор корпусу, FK
- `room_number` — номер аудиторії
- `capacity` — кількість місць

### Booking

Зберігає інформацію про бронювання аудиторій.

Атрибути:
- `booking_id` — унікальний ідентифікатор бронювання, PK
- `user_id` — користувач, який створив бронювання, FK
- `room_id` — заброньована аудиторія, FK
- `starts_at` — дата і час початку бронювання
- `ends_at` — дата і час завершення бронювання
- `purpose` — мета бронювання
- `status` — статус бронювання

### Equipment

Зберігає типи обладнання, яке може знаходитися в аудиторіях.

Атрибути:
- `equipment_id` — унікальний ідентифікатор обладнання, PK
- `name` — назва обладнання

### RoomEquipment

Асоціативна сутність між `Room` та `Equipment`.

Атрибути:
- `room_id` — ідентифікатор аудиторії, PK, FK
- `equipment_id` — ідентифікатор обладнання, PK, FK
- `quantity` — кількість одиниць цього обладнання в аудиторії

## Зв'язки

- `Building 1:N Room`
  - один корпус може містити багато аудиторій;
  - кожна аудиторія належить одному корпусу.

- `User 1:N Booking`
  - один користувач може створити багато бронювань;
  - кожне бронювання створюється одним користувачем.

- `Room 1:N Booking`
  - одна аудиторія може мати багато бронювань у різний час;
  - кожне бронювання стосується однієї аудиторії.

- `Room 1:N RoomEquipment`
  - одна аудиторія може мати багато записів про обладнання.

- `Equipment 1:N RoomEquipment`
  - один тип обладнання може бути присутній у багатьох аудиторіях.

Таким чином, зв'язок `Room M:N Equipment` реалізується через сутність `RoomEquipment`.

## Обмеження

- `User.email` повинен бути унікальним.
- У межах одного корпусу номер аудиторії не повинен повторюватися.
- Для бронювання `starts_at` повинен бути раніше за `ends_at`.
- `RoomEquipment.quantity` повинно бути більше нуля.
- Бронювання однієї аудиторії не повинні перетинатися в один і той самий час.

## Критерії прийняття

- [ ] У моделі присутні всі сутності зі spec.
- [ ] Для кожної сутності визначено первинний ключ.
- [ ] Зовнішні ключі відповідають зв'язкам між сутностями.
- [ ] Кардинальності відповідають словесному опису.
- [ ] Зв'язок M:N між Room та Equipment реалізований через RoomEquipment.
- [ ] Типи первинних та відповідних зовнішніх ключів узгоджені.
- [ ] ER-модель не містить повторюваних груп або багатозначних атрибутів.
