# Специфікація взаємодії — Завдання 3


## 1. Обраний Use Case

**UC-02 — Створити бронювання.** Мета: дозволити студенту або викладачу забронювати доступну навчальну аудиторію на визначений проміжок часу без накладання блокуючих бронювань.

У межах цієї роботи розглядається тільки UC-02 та його чотири сценарії з другої лабораторної: SC-02, SC-03, SC-07, SC-08. Діаграма для кожного сценарію зберігається в окремому файлі PlantUML.

## 2. Учасники взаємодії

| Учасник | Роль у сценаріях |
|---|---|
| Користувач (у SC-07 — перший та інший користувач) | Надсилає запит і отримує результат |
| Інтерфейс бронювання (UI) | Приймає дії користувача, передає дані сервісу та показує повідомлення |
| `BookingService` | Координує створення бронювання і перевірки |
| Університетський сервіс автентифікації | Перевіряє чинність сесії і повертає `userId` |
| `BookingRepository` | Читає активні бронювання, зберігає новий `Booking`, керує транзакцією |
| База даних | Зберігає `User`, `Room`, `Booking`, `BookingStatus` |

`BookingService`, UI і `BookingRepository` — запропоновані програмні компоненти, а не нові сутності ER-моделі першої лабораторної.

## 3. Сценарії UC-02

### SC-02 — Успішне створення бронювання

**Передумови (Lab2):** користувач автентифікований; аудиторія 301 вільна з 10:00 до 11:00.

**Послідовність (`model/sequence-01.puml`):**
1. Користувач підтверджує бронювання аудиторії 301 на 10:00–11:00.
2. UI передає запит до `BookingService`.
3. Сервіс перевіряє сесію через зовнішній сервіс автентифікації.
4. `BookingRepository` починає атомарну операцію й перевіряє актуальні блокуючі бронювання у базі даних.
5. Якщо перетинів немає, створюється **один** `Booking` для поточного `userId`.
6. Операція підтверджується, а користувач отримує повідомлення про створене бронювання.

**Очікуваний результат:** один новий запис `Booking`; повторна перевірка доступності проведена до збереження.

### SC-03 — Конфлікт при підтвердженні

**Передумови (Lab2):** користувач автентифікований; аудиторія 301 має `Confirmed`-бронювання на 10:00–11:00.

**Послідовність (`model/sequence-02.puml`):**
1. Користувач пробує забронювати аудиторію 301 на 10:30–11:30.
2. UI надсилає запит до `BookingService`, сервіс перевіряє сесію.
3. Репозиторій зчитує актуальні бронювання, що блокують цей час.
4. Перевірка виявляє перетин з наявним записом `Confirmed`.
5. Створення відхиляється; новий `Booking` не додається.
6. UI показує повідомлення про конфлікт.

**Очікуваний результат:** відмова та відсутність нового запису.

### SC-07 — Втрата доступності після пошуку

**Передумови (Lab2):** перший користувач бачив аудиторію 301 у результатах пошуку; після цього інший користувач створив блокуюче бронювання на 10:00–11:00.

**Послідовність (`model/sequence-03.puml`):**
1. Перший користувач знаходить аудиторію 301 серед доступних.
2. Інший користувач підтверджує бронювання на 10:00–11:00; система створює блокуючий `Booking`.
3. Перший користувач підтверджує раніше знайдений варіант на той самий час.
4. Сервіс **повторно** перевіряє актуальні записи в базі даних, а не довіряє старому результату пошуку.
5. Виявлено нове блокуюче бронювання. Запис для першого користувача не створюється.
6. UI повідомляє, що аудиторія вже недоступна.

**Очікуваний результат:** друге конфліктне бронювання не створюється, користувач бачить повідомлення про втрату доступності.

### SC-08 — Суміжні часові інтервали

**Передумови (Lab2):** користувач автентифікований; аудиторія 301 уже заброньована на 10:00–11:00.

**Послідовність (`model/sequence-04.puml`):**
1. Користувач підтверджує нове бронювання на 11:00–12:00.
2. Сервіс перевіряє сесію та звертається до репозиторію.
3. Репозиторій перевіряє часовий перетин з наявним бронюванням.
4. За правилом напіввідкритих інтервалів `[початок, кінець)` час 10:00–11:00 не перетинається з 11:00–12:00.
5. Система створює новий `Booking` і підтверджує результат.

**Очікуваний результат:** новий запис створюється, бо суміжні часові інтервали дозволені.

## 4. Умови й альтернативні гілки

В усіх чотирьох діаграмах показано виклики й return-повідомлення. Фрагменти `alt` відображають альтернативні результати перевірки доступності. Основна гілка кожної діаграми відповідає конкретному Gherkin-сценарію; захисні альтернативи показують, що система має робити, якщо стан змінився.

Для визначення перетину використовується правило:

`start1 < end2 AND start2 < end1`.

Записи зі статусами, у яких `BookingStatus.blocks_room = true`, враховуються як блокуючі. Діаграми застосовують `Pending` як початковий статус нових бронювань; це проєктне рішення для послідовності діаграм, а не окремий крок, прямо встановлений Gherkin.

## 5. Зв'язок із попередніми лабораторними

- **Lab1:** `User` визначає власника бронювання; `Room` — аудиторію; `Booking` — запис із часом та статусом; `BookingStatus.blocks_room` — чи зайнята аудиторія.
- **Lab2:** SC-02, SC-03, SC-07 і SC-08 визначають передумови, дії й очікуваний результат. Діаграми деталізують внутрішні повідомлення цих сценаріїв.
- Перевірка доступності перед вставленням нового `Booking` потрібна для уникнення одночасних конфліктних записів.


## 6. Технічні припущення для перевірки

Діаграми показують `beginTransactionAndLockRoom()`, `commitTransaction()` і `rollbackTransaction()` як **один можливий спосіб** атомарного створення бронювання. Друга лабораторна вимагала атомарної повторної перевірки, але не визначала конкретний механізм блокування рядка `Room`.
