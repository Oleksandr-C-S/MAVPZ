# Spec — Завдання 2: Вимоги та Use Cases

## Намір

Описати основні сценарії системи бронювання навчальних аудиторій та визначити акторів, їхні цілі й межі системи. Сценарії повинні спиратися на ER-модель першої лабораторної роботи.

## Актори

- **Користувач** — узагальнений людський актор, який шукає аудиторії та працює зі своїми бронюваннями.
- **Студент** — спеціалізація актора «Користувач».
- **Викладач** — спеціалізація актора «Користувач».
- **Сервіс автентифікації університету** — зовнішня система, яка підтверджує особу перед операціями з бронюваннями.

## Основні цілі

1. Знайти вільну аудиторію на потрібний час.
2. Створити бронювання аудиторії.
3. Переглянути власні бронювання.
4. Скасувати власне бронювання.
5. Знайти аудиторію з потрібним обладнанням.

## Зв'язок із Lab1

- `User` — власник бронювання.
- `Room` — аудиторія, яку обирають.
- `Booking` — запис про бронювання.
- `BookingStatus.blocks_room` — визначає, чи бронювання блокує аудиторію на обраний час.
- `Equipment` і `RoomEquipment` — дані для пошуку за обладнанням.

## Критерії прийняття

- [ ] Вимоги сформульовані у форматі EARS і можуть бути перевірені.
- [ ] Для основних цілей написані user stories та Gherkin-сценарії.
- [ ] На діаграмі показані людські актори та зовнішній сервіс.
- [ ] Використано узагальнення акторів, `include` та `extend`.
- [ ] Матриця трасування показує зв'язки багато-до-багатьох.
- [ ] Є принаймні одна непокрита вимога з поясненням.
- [ ] Сценарії не суперечать сутностям та зв'язкам Lab1.

## Потребує уточнення під час роботи

На етапі побудови діаграми перевірити, які сценарії є обов'язковими частинами інших (`include`), а які — лише необов'язковим розширенням (`extend`).
