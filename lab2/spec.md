# Spec — Завдання 2: Вимоги та Use Cases

## Намір

Описати основні сценарії системи бронювання навчальних аудиторій та визначити акторів, їхні цілі й межі системи. Сценарії повинні спиратися на ER-модель першої лабораторної роботи.

## Актори

- **Користувач** — узагальнений людський актор, який шукає аудиторії та працює зі своїми бронюваннями.
- **Студент** — спеціалізація актора «Користувач».
- **Викладач** — спеціалізація актора «Користувач».
- **Сервіс автентифікації університету** — зовнішня система, яка підтверджує особу перед операціями з бронюваннями.

## Основні цілі

1. Знайти вільну аудиторію на потрібний час.
2. Створити бронювання аудиторії.
3. Переглянути власні бронювання.
4. Скасувати власне бронювання.
5. Знайти аудиторію з потрібним обладнанням.

## Попередній перелік Use Cases

| ID | Use Case | Основний актор |
|---|---|---|
| UC-01 | Переглянути доступні аудиторії | Користувач |
| UC-02 | Створити бронювання | Користувач |
| UC-03 | Скасувати бронювання | Користувач |
| UC-04 | Переглянути мої бронювання | Користувач |
| UC-05 | Фільтрувати за обладнанням | Користувач |
| UC-06 | Автентифікувати користувача | Сервіс автентифікації університету |
| UC-07 | Перевірити доступність аудиторії | Внутрішній сценарій |

## Зв'язок із Lab1

- `User` — власник бронювання.
- `Room` — аудиторія, яку обирають.
- `Booking` — запис про бронювання.
- `BookingStatus.blocks_room` — визначає, чи бронювання блокує аудиторію на обраний час.
- `Equipment` і `RoomEquipment` — дані для пошуку за обладнанням.

## Правила часових інтервалів (уточнення AUD-01)

- Кожне бронювання має `starts_at < ends_at`.
- Час бронювання розглядається як напіввідкритий інтервал `[starts_at, ends_at)`: початок включається, завершення не включається.
- Два бронювання A та B перетинаються лише тоді, коли одночасно виконуються `A.starts_at < B.ends_at` і `B.starts_at < A.ends_at`.
- Якщо A завершується рівно тоді, коли B починається, перетину немає.
- Конфлікт виникає лише між бронюваннями **однієї аудиторії**, статуси яких мають `BookingStatus.blocks_room = true`.
- Ці правила застосовуються під час пошуку (UC-01 / UC-07) і повторної перевірки перед створенням бронювання (UC-02 / UC-07).

## Правило повторної перевірки перед збереженням (AUD-02)

- Результат UC-01 — це попередній список доступних аудиторій, а не гарантія, що аудиторія залишиться вільною до підтвердження.
- Під час UC-02 система після успішної автентифікації та отримання підтвердження від користувача **повторно виконує UC-07** для обраної `Room` і часового інтервалу.
- Повторна перевірка враховує всі актуальні бронювання цієї аудиторії, для яких `BookingStatus.blocks_room = true`, за правилами напіввідкритих інтервалів з AUD-01.
- **Лише якщо конфлікту немає**, система створює `Booking`. Якщо він з'явився після пошуку, система не створює запис і повідомляє, що аудиторія вже зайнята.
- Перевірка та створення повинні виконуватися як одна атомарна операція з погляду конкурентних бронювань. Спосіб технічної реалізації не визначається цією Use Case-моделлю.

## Правила скасування бронювання (AUD-03)

- UC-03 доступний лише автентифікованому користувачу. Перед зміною статусу система перевіряє, що `Booking.user_id` дорівнює ідентифікатору поточного `User`.
- У поточній версії дозволено скасовувати власні бронювання зі статусами `Pending` або `Confirmed`. Обидва статуси мають `BookingStatus.blocks_room = true`.
- У разі успішного скасування статус `Booking` змінюється на `Cancelled`, для якого `blocks_room = false`; сам запис `Booking` не видаляється.
- Якщо бронювання належить іншому користувачу або має статус `Cancelled` чи `Rejected`, система не змінює його і повідомляє про відмову. Повторне скасування вже скасованого запису заборонене.
- Система використовує наявні `Booking.user_id`, `Booking.status_id` та `BookingStatus` із Lab1. Додаткові поля в ER-моделі для цього сценарію не потрібні.

## Критерії прийняття

- [ ] Вимоги сформульовані у форматі EARS і можуть бути перевірені.
- [ ] User story записані безпосередньо як Gherkin-сценарії (Given/When/Then), без окремого документа user stories.
- [ ] На діаграмі показані людські актори та зовнішній сервіс.
- [ ] Використано узагальнення акторів, `include` та `extend`.
- [ ] Матриця трасування показує зв'язки багато-до-багатьох.
- [ ] Є принаймні одна непокрита вимога з поясненням.
- [ ] Сценарії не суперечать сутностям та зв'язкам Lab1.
- [ ] Суміжні інтервали не вважаються конфліктними; правило перетину формально визначене.
- [ ] UC-02 обов’язково включає повторний UC-07 безпосередньо перед створенням Booking.
- [ ] UC-03 допускає скасування тільки власного `Pending` або `Confirmed` бронювання; інші випадки відхиляються без зміни даних.
- [ ] Конфлікт, що виник після пошуку, не призводить до створення Booking; перевірка і збереження захищені від конкурентного створення.

## Зв’язки сценаріїв на діаграмі

- `UC-01` включає `UC-07` для перевірки доступності аудиторій під час пошуку.
- `UC-02` включає `UC-06` (автентифікація) та `UC-07` (перевірка доступності перед створенням бронювання).
- `UC-03` і `UC-04` включають `UC-06`, оскільки ці операції потребують автентифікації.
- `UC-05` розширює `UC-01` через `extend`: фільтр обладнання необов’язковий.

Ці зв’язки наведено у `model/usecases.puml`. Атомарність повторної перевірки та створення бронювання встановлено текстовою вимогою, а не самою стрілкою `include`.
