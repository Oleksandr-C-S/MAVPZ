## 1. Призначення моделі

У цій роботі розглядається архітектура системи бронювання навчальних аудиторій, яку я використовував у попередніх лабораторних. Основна задача — показати, на які компоненти розділена система, за що кожен із них відповідає та через які інтерфейси відбувається взаємодія. Для моделювання обрано UML Component Diagram у PlantUML.

Головним прикладом є UC-02 — створення бронювання. Перед створенням нового запису система перевіряє користувача та доступність аудиторії на вибраний час. Нове бронювання має початковий статус `Pending`.

## 2. Компоненти та їхня відповідальність

| Компонент | Призначення |
|---|---|
| `Web UI` | Отримує дії студента або викладача, передає запити та відображає результат |
| `Booking API` | Приймає звернення від інтерфейсу та передає їх до бізнес-логіки |
| `BookingService` | Координує створення бронювання, автентифікацію, перевірку доступності та запис даних |
| `AvailabilityService` | Перевіряє, чи не зайнята аудиторія в запитаний часовий інтервал |
| `AuthenticationAdapter` | Звертається до зовнішнього університетського сервісу для перевірки сесії |
| `BookingRepository` | Читає та записує бронювання, працює з транзакціями та блокуючими статусами |
| `RoomRepository` | Надає дані про аудиторії з бази даних |
| `Booking Database` | Зберігає сутності предметної області з першої лабораторної |

`Booking Database` містить `User`, `Building`, `Room`, `Booking`, `BookingStatus`, `Equipment` і `RoomEquipment`. Сервіси не звертаються до таблиць напряму: для цього використовуються репозиторії.

## 3. Інтерфейси та залежності

На діаграмі назви інтерфейсів записані біля стрілок. Компонент на початку стрілки використовує (*required*) відповідний контракт, а компонент у кінці його надає (*provided*).

| Інтерфейс | Хто використовує | Хто надає |
|---|---|---|
| `IBookingApi` | `Web UI` | `Booking API` |
| `IBookingService` | `Booking API` | `BookingService` |
| `IAvailabilityService` | `BookingService` | `AvailabilityService` |
| `IAuthentication` | `BookingService` | `AuthenticationAdapter` |
| `IBookingRepository` | `BookingService`, `AvailabilityService` | `BookingRepository` |
| `IRoomRepository` | `AvailabilityService`, `BookingService` | `RoomRepository` |

Залежності спрямовані від компонентів, які потребують функції, до компонентів, що ці функції надають. Конкретні методи кожного інтерфейсу на цьому етапі не деталізуються: завдання полягає в моделюванні архітектурних меж.

## 4. Межа системи та зовнішня інтеграція

У прямокутнику «Система бронювання аудиторій» знаходяться власні компоненти застосунку та база даних. Студент або викладач взаємодіє із системою через `Web UI`.

Університетський сервіс автентифікації розташований **поза межею системи**, оскільки його робота не належить до внутрішньої реалізації бронювання. `AuthenticationAdapter` надсилає `validateSession(session)` та обробляє результати `valid(userId)`, `invalid` або `timeout`. Так бізнес-логіка не залежить безпосередньо від деталей зовнішнього сервісу.

## 5. Як створюється бронювання

1. Користувач вибирає аудиторію та час у `Web UI`.
2. `Web UI` передає запит через `Booking API` до `BookingService`.
3. `BookingService` використовує `AuthenticationAdapter` для перевірки сесії.
4. `AvailabilityService` перевіряє доступність через репозиторії. Враховуються бронювання, статус яких має `BookingStatus.blocks_room = true`.
5. Перед збереженням доступність перевіряється повторно. Якщо конфлікту немає, `BookingRepository` записує нове бронювання зі статусом `Pending`; якщо є — створення відхиляється.
6. Результат повертається користувачу через API та інтерфейс.

Для перевірки перетину часових проміжків використовується підхід із Lab2: суміжні інтервали, наприклад 10:00–11:00 і 11:00–12:00, не конфліктують.

## 6. Узгодженість із попередніми лабораторними

- **Lab1 (ER-модель):** база даних містить ті самі сутності; власник бронювання визначається через `Booking.user_id`, а блокування — через `BookingStatus.blocks_room`.
- **Lab2 (вимоги та Use Cases):** `BookingService` підтримує UC-02 та повторну перевірку доступності з REQ-02A. Окремий `AvailabilityService` відповідає за перевірку конфліктів.
- **Lab3 (Sequence Diagram):** взаємодія UI, сервісу бронювання, репозиторіїв і БД зберігає ту саму послідовність відповідальностей; окремо показано зовнішню перевірку користувача.
- **Lab4 (Activity Diagram):** архітектура дозволяє виконати перевірки, обробити відмову або тайм-аут автентифікації та завершити процес без створення `Booking`, якщо умови не виконані.

## 7. Обґрунтування поділу на компоненти

Я розділив бізнес-логіку та роботу з базою даних, щоб правила бронювання не залежали від конкретних SQL-запитів. Перевірку доступності виніс в окремий сервіс, оскільки вона потрібна не тільки під час створення бронювання, а й під час пошуку аудиторій. Для зовнішньої автентифікації використав адаптер, щоб у решті системи був один зрозумілий інтерфейс взаємодії.

Такий поділ робить залежності між частинами системи чіткішими. Водночас ця діаграма є архітектурною моделлю, а не готовою реалізацією: конкретні технології бази даних, розгортання компонентів та детальні сигнатури методів тут не визначаються.
