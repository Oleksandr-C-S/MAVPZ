## 1. Намір і межа

Модель деталізує лише UC-02 «Створити бронювання». Мета — показати, через які частини системи проходить запит користувача, де відбуваються перевірки і хто відповідає за запис у БД. Важливо не допустити двох бронювань однієї аудиторії на час, що перетинається (REQ-02A). Діаграма показує залежності компонентів, а не всі внутрішні методи.

## 2. Компоненти та відповідальність

| Компонент | Для чого потрібен |
|---|---|
| Web UI | Введення даних і відображення результату |
| HTTP вхід `<<port>>` | Точка входу запитів до бекенду |
| Booking API | Приймає запит і передає його бізнес-логіці |
| BookingService | Координує перевірку сесії, доступності та рішення про створення/відмову |
| AvailabilityService | Попередній пошук доступних аудиторій; його результат не бронює місце |
| AuthenticationAdapter | Перекладає внутрішній запит перевірки сесії в зовнішній виклик |
| Вихід Auth `<<port>>` | Точка виходу запиту до університетського сервісу |
| BookingRepository | Транзакція, блокування Room, повторна перевірка, INSERT, commit/rollback |
| RoomRepository | Читання даних про аудиторії |
| Booking Database | Дані `User`, `Building`, `Room`, `Booking`, `BookingStatus`, `Equipment`, `RoomEquipment` |
| Університетський сервіс автентифікації `<<external>>` | Зовнішній постачальник перевірки сесії |

База даних — окрема частина системи, а не компонент усередині пакета репозиторіїв. Зовнішній сервіс розміщено поза межею системи бронювання.

## 3. Контракти

| Інтерфейс | Надає (provided) | Використовує (required) |
|---|---|---|
| `IBookingApi` | Booking API | Web UI |
| `IBookingService` | BookingService | Booking API |
| `IAvailabilityService` | AvailabilityService | BookingService |
| `IAuthentication` | AuthenticationAdapter | BookingService |
| `IBookingRepository` | BookingRepository | BookingService, AvailabilityService |
| `IRoomRepository` | RoomRepository | BookingService, AvailabilityService |
| `ISessionValidation` | Зовнішній університетський сервіс | Вихідний порт Auth / AuthenticationAdapter |

Стрілка `..|>` показує надання інтерфейсу, а `..>` — залежність від нього. Два позначені `<<port>>` елементи — логічні порти бекенду, а не окремі бізнес-сервіси.

## 4. Основний сценарій UC-02

1. Web UI надсилає HTTP-запит через вхідний порт до Booking API. API звертається до BookingService.
2. BookingService перевіряє сесію через IAuthentication. AuthenticationAdapter надсилає `validateSession(session)` через вихідний порт до інтерфейсу `ISessionValidation` університетського сервісу. Можливі `valid(userId)`, `invalid` і `timeout`; у двох останніх випадках бронювання не створюється.
3. AvailabilityService може попередньо знайти доступні аудиторії. Це не гарантує доступності в момент збереження.
4. Для запису BookingService викликає `beginAtomicBooking(...)`. BookingRepository робить `beginTransactionAndLockRoom(roomId)` і `findBlockingBookings(...)`, після чого повертає `availabilityResult`.
5. Якщо аудиторія вільна, BookingService викликає `insertBooking(..., Pending)`, репозиторій виконує INSERT і commit. Якщо є конфлікт, BookingService викликає `rollbackTransaction()`. Перевірка і запис проходять у межах однієї транзакції.

Перетин інтервалів перевіряється для `[start, end)`, зважаючи на `BookingStatus.blocks_room`. Два проміжки, які тільки стикаються кінцями, не конфліктують.

## 5. Критерії прийняття

- На діаграмі є Web UI, API, бізнес-сервіси, репозиторії та окрема БД.
- Відображено межу системи й межу бекенду, HTTP-вхід і вихід автентифікації.
- Зовнішній Auth показаний компонентом `<<external>>`, що **надає** `ISessionValidation`; внутрішній адаптер його **споживає**.
- Для шести внутрішніх інтерфейсів зрозуміло, хто постачальник і хто споживач.
- Видно розподіл обов'язків BookingService / BookingRepository і повторну перевірку в транзакції (REQ-02A).
- У переліку даних є Building із Lab1, статус Pending і результати автентифікації з Lab4.
- Текст і PNG відповідають актуальному `components.puml`, а вихідний файл рендериться без помилок.

## 6. Поза обсягом

Діаграма навмисно деталізує лише **UC-02**. Сценарії **UC-03, UC-04, UC-05** не розкладені на окремі компоненти або виклики, хоча в загальній системі можуть використовувати ті самі UI, API й репозиторії. Перевірка права власності **NFR-04** і нагадування **REQ-07** також не моделюються в цьому UC-02-огляді: тут немає окремих компонентів авторизації власника чи планувальника нагадувань. Це не означає, що вимоги скасовані — для них потрібне окреме розширення архітектури. Конкретні HTTP-маршрути, обрана СУБД, формат мережевого протоколу Auth і розгортання сервісів також не деталізуються.
