## 3. Ключове рішення та альтернативи

Activity Diagram підходить для цього завдання, оскільки показує весь процес бронювання, а не тільки зміну станів одного об'єкта. У BPMN також можна описати такий процес, але для цієї роботи достатньо Activity Diagram.

Перевірка часового інтервалу та автентифікація можуть виконуватися паралельно, бо не залежать одна від одної. Створення бронювання можливе тільки після завершення обох перевірок.

Якщо сервіс автентифікації не відповідає, процес передбачає завершення перевірки за тайм-аутом без створення Booking. Контекст попереднього пошуку потрібен для вибору повідомлення користувачу, а не для визначення актуальної доступності. Повторна перевірка та створення запису виконуються в межах транзакції.

## 4. Узгодженість із попередніми лабораторними

| Сценарій | Шлях в Activity Diagram |
|---|---|
| SC-02 | Доступна аудиторія → insertBooking → commit → showConfirmation |
| SC-03 | Конфлікт → rollback → showConflictMessage |
| SC-07 | Втрата доступності після пошуку → rollback → showAvailabilityLostMessage |
| SC-08 | Суміжний інтервал без перетину → створення Booking |

За результатами аудиту уточнено передачу `userId`, контекст попереднього пошуку та повідомлення сервісу автентифікації. Зв'язок із ER-моделлю забезпечують `Booking.user_id`, `Booking.room_id` і статуси `Pending` та `Confirmed`, які блокують аудиторію. Повідомлення `validateSession(session)`, `validSession(userId)` та повідомлення про результат відповідають взаємодіям Lab3. Тайм-аут і паралельна локальна перевірка — проєктні уточнення Lab4.
